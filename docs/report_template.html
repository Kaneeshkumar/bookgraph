1. Abstract

The BookGraph – Library Book Recommendation System is a software project developed to simplify and automate campus library book discovery, catalogue exploration, and circulation management using NoSQL Graph Database (Neo4j) principles. In many educational institutions, library records are maintained either through flat spreadsheets or legacy relational database tables. Because relationships between books, students, authors, and genres are modeled merely through disconnected foreign key columns, crucial contextual relationships remain hidden. Finding patterns such as co-borrowing affinity or collaborative peer suggestions in a table-based system demands complex, multi-table Cartesian joins that scale poorly and execute slowly.

This project addresses these problems by modeling library entities as a Labeled Property Graph (LPG). Students, Books, Authors, and Genres are modeled directly as nodes, while domain interactions such as (:Student)-[:BORROWED]->(:Book), (:Student)-[:RATED]->(:Book), (:Book)-[:WRITTEN_BY]->(:Author), and (:Book)-[:BELONGS_TO]->(:Genre) are stored as first-class directional edges with rich properties.

The main objective of this project is to demonstrate how NoSQL graph databases transform a monolithic, slow library search system into a fast, relationship-centric discovery engine. The system supports three major recommendation paradigms:

  • Collaborative Filtering: Discovers readers with overlapping borrowing histories and recommends unread books those peers checked out.
  • Content-Based Filtering: Scores reader affinity across academic subject genres and favorite authors.
  • Degrees of Reading Separation: Applies breadth-first graph traversal (shortestPath) to discover how any two campus readers are linked via shared books.

By taking advantage of Neo4j's index-free adjacency and the expressive Cypher query language, BookGraph delivers $O(1)$ constant-time traversal per relationship hop. Backed by a modern Node.js and Express backend with a 2D physics visualizer (Vis.js Network), the project provides an intuitive and transparent library discovery platform.

2. Introduction and Literature Survey

Introduction

College libraries hold tens of thousands of academic volumes, textbooks, and research proceedings. Traditionally, students search the library catalogue using an exact title string, author surname, or subject keyword and receive an isolated list of matching items. Relational library management approaches treat past borrowing logs merely as audit trails for calculating late fines and tracking returns rather than utilizing them to power intelligent book discovery.

Managing interconnected relationships in relational databases requires joins across intermediate associative junction tables. As circulation tables grow into hundreds of thousands of rows, multi-hop queries (such as "find books borrowed by students who borrowed the same books as Student A") incur exponential latency. Graph databases store relationships as direct memory pointers alongside nodes on disk. BookGraph leverages this principle to provide explainable recommendations and interactive graph exploration.

Literature Survey

J. Webber and I. Robinson (2015) showed that graph databases outperform relational databases by orders of magnitude on connected datasets. Their empirical benchmarks proved that while relational join latency scales exponentially as query path length increases, graph databases maintain predictable, sub-second query latency through index-free adjacency [1].

C. Angles and C. Gutierrez (2018) surveyed graph data models, establishing that the Labeled Property Graph (LPG) provides superior flexibility for modeling multi-relational networks with rich edge metadata (e.g., loan timestamps and star ratings) compared to rigid relational schemas [2].

M. Kleppmann (2017) detailed the architectural trade-offs in modern data systems, showing how graph pattern matching eliminates the object-relational impedance mismatch and simplifies collaborative filtering that otherwise requires offline matrix batch computations [3].

S. Russell and P. Norvig (2020) formalized collaborative filtering algorithms, which BookGraph realizes natively in Cypher by matching bipartite graph motifs: (Student)-[:BORROWED]->(Book)<-[:BORROWED]-(Peer)-[:BORROWED]->(RecBook) [4].

Problem Statement

The legacy library management architecture presents severe performance and usability limitations:

  • Hidden Relationships: Relational tables decouple students, books, and genres into isolated tables, obscuring natural reading clusters.
  • Join Cost: Finding books borrowed by students with identical reading histories requires 4 to 6 SQL JOIN operations, leading to high memory overhead.
  • Rigid Schemas: Introducing dynamic metadata (e.g., student reviews, star ratings, or genre shelves) requires schema alterations and table locks.
  • Lack of Transparency: SQL results present tabular rows without explainability for why a book was suggested.

Graph Traversal Walkthrough — Collaborative Recommendation

When a student requests recommendations, the system avoids relational joins by executing a 3-hop traversal:

  1. Hop 1 (Outbound Borrow): Starts at target student node (me:Student {usn: $usn}) and traverses outgoing [:BORROWED] edges to books read by the student: (shared:Book).
  2. Hop 2 (Inbound Peer): Traverses backward along incoming [:BORROWED] edges from those shared books to find other readers who borrowed them: (peer:Student).
  3. Hop 3 (Candidate Expansion): Traverses forward from those peers along outgoing [:BORROWED] edges to find candidate books (rec:Book).
  4. Set Difference & Ranking: Filters out any candidate book that me has already read (WHERE NOT (me)-[:BORROWED]->(rec)) and orders by peer frequency (count(DISTINCT peer) DESC).

6. Recommendation Algorithms & Cypher Queries – Unit III

6.1 Collaborative Filtering Query

MATCH (me:Student {usn: $usn})-[:BORROWED]->(shared:Book)<-[:BORROWED]-(peer:Student)
WHERE me <> peer
MATCH (peer)-[:BORROWED]->(rec:Book)
WHERE NOT (me)-[:BORROWED]->(rec)
OPTIONAL MATCH (rec)-[:WRITTEN_BY]->(a:Author)
OPTIONAL MATCH (rec)-[:BELONGS_TO]->(g:Genre)
RETURN rec.id AS BookID,
       rec.title AS Title,
       collect(DISTINCT a.name) AS Authors,
       g.name AS Genre,
       count(DISTINCT peer) AS PeerScore,
       collect(DISTINCT peer.name) AS RecommendedByStudents
ORDER BY PeerScore DESC, Title ASC
LIMIT 5;

6.2 Content-Based Genre Affinity Query

MATCH (me:Student {usn: $usn})-[:BORROWED]->(:Book)-[:BELONGS_TO]->(g:Genre)
WITH me, g, count(*) AS genreScore
ORDER BY genreScore DESC
LIMIT 2
MATCH (rec:Book)-[:BELONGS_TO]->(g)
WHERE NOT (me)-[:BORROWED]->(rec)
OPTIONAL MATCH (rec)-[:WRITTEN_BY]->(a:Author)
RETURN rec.id AS BookID,
       rec.title AS Title,
       g.name AS Genre,
       collect(DISTINCT a.name) AS Authors,
       genreScore AS AffinityScore
ORDER BY genreScore DESC, rec.year DESC
LIMIT 5;

6.3 Degrees of Reading (Shortest Path Traversal)

MATCH p = shortestPath(
  (s1:Student {usn: $s1})-[:BORROWED*]-(s2:Student {usn: $s2})
)
RETURN [node IN nodes(p) | coalesce(node.title, node.name)] AS PathSequence,
       length(p) AS DegreeDistance;

6.4 Book Checkout Mutation (Transactional Edge Creation)

MATCH (s:Student {usn: $usn}), (b:Book {id: $bookId})
CREATE (s)-[r:BORROWED {borrow_date: $today, return_date: $dueDate, status: 'ACTIVE'}]->(b)
RETURN r;

9. Discussion of Results & Trade-Offs

The implementation confirms that modeling institutional library records as a graph eliminates the latency and complexity of relational joins. In the original relational design, recommending books based on reader circles required querying three tables (Students, Issues, Books) with multiple join predicates. In Neo4j, Cypher pattern matching concisely captures this intent in a single declarative expression.

Trade-Offs: Graph databases introduce overhead when performing high-volume bulk aggregation across disjoint nodes (e.g., computing global fines across the entire college). For pure transactional record-keeping without relationship queries, a relational store is sufficient. However, for recommendation systems, circulation tracking, and knowledge discovery, graph databases are vastly superior.

10. Conclusion and Future Work

BookGraph successfully demonstrates the practical implementation of a NoSQL graph database in library management. By modeling students, books, authors, and genres as nodes and their borrowing and rating actions as relationships, the system delivers high-performance collaborative filtering, content-based recommendations, and graph centrality analytics.

Future Enhancements:

  • Integration with the Neo4j Graph Data Science (GDS) library for community detection (Louvain algorithm) and Node2Vec embeddings.
  • Role-based authentication using JWT for students and librarians.
  • Integration with physical barcode / RFID scanners for automated counter checkout.
